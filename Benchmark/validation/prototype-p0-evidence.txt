2. P0 验证矩阵
--------------------------------------------------------------------------------
[1] 三个 consteval 操作族
  register_plugin(const char(&)[N]) / declare_dependencies(identity, groups) / sort_and_validate(catalog, selected)
  证据：include/FixturePluginApi.hpp；FixturePlan.cpp、28 个 case TU、8 个 scale TU 均真实编译。
  三者都是 consteval：运行期调用会直接编译失败，因此不可能出现"运行期改写单例"。

[2] 二维不等长与空外层
  tuple-of-arrays（各组长度不同）与矩形重载都实现；空外层 std::tuple<> 合法；
  空内层 std::array<std::string_view,0> 被诊断为 EmptyRequirementGroup（case_empty_inner_group）。
  生成器侧同样用 tuple（每组一个 std::array + std::tuple{...}），与手写路径同一入口。

[3] 拥有存储 / 复制无悬空 view
  src/assembly/FixtureDeterminism.cpp（编译期 static_assert）：
  - 从局部 char 缓冲区构造身份后把缓冲区整块改写，身份仍返回原名字；
  - 声明的候选同样持有副本；PluginIdentity / PluginDeclaration 都是 trivially copyable；
  - 复制后的身份、声明、AssemblyResult 仍可读。
  PluginIdentity 里保留 16 字节前缀字（prefix0/prefix1），仍是从名字字节派生的冗余副本，
  不是 view；sizeof(PluginIdentity) ≤ 144 由 static_assert 固定。
  本轮把候选改成**紧凑拥有存储**（SoA）：
  - 逐候选只存 (length, offset, id, prefix0, prefix1) 五个标量，名字字节按实际长度写进
    candidate_pool；池按"候选上限 × 名字上限"预留，是拥有语义下的最坏情况上界；
  - 名字仍然完整保存，比对时先比标量键、必须时再逐字节确认——**没有**退化成"只比碰撞哈希"，
    也没有返回指向常量求值局部对象的 view；
  - 候选校验路径每个候选只碰 30 字节标量 + 必要的名字字节，不再复制 144 字节身份结构。
  候选名字的读取统一走 PluginDeclaration::candidate_view(index)（FixtureDeterminism 已改用该入口）。

[4] JSON → CMake → C++ 闭环
  单一源：plugins/fixture_alpha/plugin.json、plugins/fixture_beta/plugin.json；
           catalog：assembly/catalog.cmake；profile：fixture_default.json(2)、fixture_zero.json(0)。
  CMake 解析（cmake/IDFixtureResolve.cmake）实测输出：
      fixture 产品选择：ID.Fixture.Alpha;ID.Fixture.Beta
      fixture 链接边  ：IDFixtureBeta|IDFixtureAlpha|IDFIXTUREALPHA
      fixture 零插件选择数：（空）
  派生并真实生效：
      - 逐需求 provider（0 个/多个直接 FATAL_ERROR，不按顺序挑）；
      - 真实链接边 → target_link_libraries(Beta PUBLIC Alpha)；
      - PUBLIC 身份宏 → Beta 编译宏：-DID_FIXTURE_BETA_BUILD_DLL=1 -DID_USE_PLUGIN_IDFIXTUREALPHA=1
        Alpha 编译宏：-DID_FIXTURE_ALPHA_BUILD_DLL=1（没有任何身份宏，证明未无差别注入）
        Beta 源码 #if !defined(ID_USE_PLUGIN_IDFIXTUREALPHA) → #error，缺宏直接编译失败；
        Beta 源码 #if defined(ID_FIXTURE_ALPHA_BUILD_DLL) → #error，证明上游 build 宏未向下传播。
      - 构建证据（选中集合/逐需求 provider/链接边）→ 生成头 → C++ compare_evidence 逐项比对。
  本轮修正（计划书 8.4 的局部要求）：
      - 生成头不再用 file(WRITE) 直接写最终文件，改为 templates/Assembly.generated.hpp.in +
        configure_file(@ONLY)（内容不变时不刷新时间戳）；
      - 每个 plugin.json 与 profile 都 set_property(DIRECTORY APPEND PROPERTY CMAKE_CONFIGURE_DEPENDS)，
        改 JSON 后无需手工清缓存即可重新配置。

[10] 反向编译用例（28 条 + 合法对照 + 两个驱动器自检）
  驱动器：cmake/RunNegativeCases.cmake（自定义目标 FixtureNegativeCases）。
  判定（缺一不可，见脚本头部注释）：
      合法对照 exit 0；目标 exit != 0；输出含静态断言失败文本；
      失败条数**恰好 1**（只允许类别断言失败，辅助断言不得单独失败）；
      输出含 ID_ASSEMBLY_ERROR_EXPECTED:<类别>；输出**不含** ID_ASSEMBLY_ERROR_MISMATCH。
      静态断言失败文本取 GNU 措辞 "static assertion failed"：本机只有 GCC 16.2.0 实测，
      MSVC / clang 未安装、未验证；措辞或计数方式不同时必须重新核实，不能把本批结论平移过去。
  机制：CaseCommon.hpp 的 error_matches<Expected> 与 error_differs<Expected> 是一对互斥的
  常量谓词，配成两条 static_assert：
      实际类别 == 期望 → 只有 error_differs 失败，消息带 EXPECTED:<类别>；
      实际类别 != 期望 → 只有 error_matches 失败，消息带 MISMATCH:<类别>。
  所以"任意错误都算通过"的假阳性不可能出现；期望类别写错时必然出现 MISMATCH。
  新增的"失败条数 == 1"判据补的是另一类假阳性：类别断言对、但环闭合/成员集合/边界前置等
  辅助断言单独失败时，输出仍然"有 EXPECTED、没有 MISMATCH"。实测该情形会产生 2 条失败，
  因此"恰好 1 条"能把它判掉；这也说明 28 条的通过不是靠删掉辅助断言换来的。
  日志布局（本轮修正，见第 8 节）：每个构建模式写自己的目录，逐条名字不再需要人工区分：
      raw/protoshared/negative-<case>.log        SHARED 的 28 条完整编译输出
      raw/protostatic/negative-<case>.log        STATIC 的 28 条完整编译输出
      raw/<mode>/negative-legal-control.log      同环境合法对照
      raw/<mode>/negative-wrong_expectation.log  自检一（期望类别写错）
      raw/<mode>/negative-aux_assert_failure.log 自检二（类别对、辅助断言失败）
      raw/<mode>/negative-summary.log            汇总
      raw/<mode>/negative-index.txt              可复核索引（构建目录/CWD/工具链/逐条判定列）
      raw/<mode>/batch-owner.txt                 目录归属（被别的构建目录复用时报错）
      raw/<mode>/negative-batch-stdout.log       批次控制台输出（含 configure 与判定行）
      raw/<mode>/negative-batch-command.txt      批次命令 / shell CWD / EXIT / 运行时间
  每条日志头部自带 MODE / BUILD_DIR / CWD / TARGET / EXPECTED_MARKER / COMMAND / EXIT /
  STATIC_ASSERT_FAILED_COUNT / HAS_EXPECTED / HAS_MISMATCH，可离线逐项复核。
  旧布局（raw root 下的 negative-<case>.log 与手工改名的 summary）只保留了 9 条 STATIC 副本，
  其余 19 条不存在（同名文件的时间戳落在随后的 SHARED 批次里），不再作为 28/28 的证据；
  如实说明见第 8 节。

[11] 容量上限契约

  都已在实现里强制：

    - sort_and_validate 的收集阶段**在任何结果索引写入之前**再复核一遍（防止绕过声明期诊断）；
    - provider 行宽固定 kMaxRequirements，绑定值先写临时行，整插件合法后才写结果索引；
    - catalog 数量超过 256 时，诊断来自 sort_and_validate 的
      `if constexpr (kCatalogSize > kMaxCatalog) { TooManyCatalog; return; }` **提前返回**。
      更正（本轮）：上一版本把这里写成"在收集第 257 条时报 TooManyCatalog"，与实现不符——
      这条输入形状下 collect_entry 的 `catalog_count >= kMaxCatalog` 守卫**不会被执行**，
      它只是"声明元组长度被绕过"时的防御性护栏。诊断类别不变，但机制叙述必须如实。
    - 组内重复候选的诊断位置也从声明期移到绑定阶段（catalog 下标位图，O(k)），
      类别仍是 DuplicateCandidate；见 [15] 的错误优先级说明。
  合法对照：32 组、16 候选、256 条、128 active 各有一条通过的 TU（见 [10] 与第 3 节）。

[12] 环诊断（本轮扩容 + 真实闭环）
  case_cycle（2 节点）与 case_cycle_long（9 节点环 + 2 个环下游残余节点）都断言：
    error_is_cycle == true、error_node_count == 环长度、成员恰为环上节点、且
    CaseCommon::cycle_path_is_closed 逐条验证 error_nodes[i+1] 是 error_nodes[i] 的真实上游、
    末尾回到 error_nodes[0]。
  实现（旧的 8 成员上限已删除，容量改为 kMaxActive=128）：
    从任一未排序节点沿"下游 -> 上游"游走。任何未排序节点都至少有一个未排序上游——
    它从未把入度减到 0，而能减到 0 的前提是全部上游都已排序；因此游走必然在 ≤active 步内
    遇到重复节点，第一次重复的位置就是环入口。丢掉环之前的残余前缀后，剩下的成员即真实环。
    error_nodes 的方向口径固定为"下游在前、上游在后、末尾闭合回首个"，因此残余下游节点
    （例如 Tail.0 -> Ring.0、Tail.1 -> Tail.0）不会被算作环成员。
  为什么旧实现会错：记录数组写死 8 个，9 节点环在第 8 个成员处退出循环且 error_is_cycle 保持 false；
  另外它从"第一个仍有入度的节点"沿正向边（provider -> dependent）前进，起点若是纯残余下游
  就会走进死胡同并只记录残余节点。

[13] 哈希碰撞（合法身份 + 强制 ID）与同前缀长名回归
  FixtureTestSupport::make_colliding_identity 复制合法名字后强制写入 Alpha 的真实 ID。
  非法分支先 static_assert 该夹具 is_valid == true（证明不是 InvalidName 兜底），
  再要求类别严格等于 NameHashCollision。实现按"先比 ID、再比长度+前缀+字节"判定：
  同 ID 但名字不同 → NameHashCollision；同 ID 同名 → DuplicatePlugin。
  本轮修掉一条真实缺陷：绑定阶段的自依赖判等只比 (长度, ID, prefix0, prefix1)，
  对超过 16 字节的名字等价于"前缀 + 哈希相同即同名"，于是真实碰撞会被误报成 SelfDependency。
  现在自依赖必须**完整名字相等**（name_equals 先比标量键，键全同再逐字节确认）。
  回归用例 case_self_dependency_prefix_collision：两个 17 字节名字前 16 字节相同、第 17 字节不同，
  候选被强制成"自身 ID"，期望类别是 NameHashCollision（旧实现报 SelfDependency）；
  同 TU 的合法对照用真实哈希，A 依赖 B 必须组装成功，并断言强制 ID 后类别确实变成碰撞。

[15] 构建证据比对（compare_evidence）：双向一一匹配 + 索引前边界检查
  旧实现的两个漏洞（本轮修复，均由新增反向用例锁定）：
    - 只检查"每条证据名字/记录能在计划里找到 + 数量相等"，因此
      selected{Alpha,Alpha} 可以顶替 {Alpha,Beta}、两条相同 provider 记录可以顶替
      "两个不同需求各绑一个上游"、两条相同边可以顶替另一条边；
    - 证据计数大于数组容量时会先按下标读再判断，等于在常量求值里越界访问。
  现实现：
    - 选中集合：count 必须等于 plan.active_count 且不超过证据容量；每条名字必须命中一个
      **尚未被消费**的 active 下标（consumed_active 位图）；
    - 逐需求绑定：count 必须等于所有 active 的 active_requirement 之和且不超过证据容量；
      每条记录消费一个不同的 (active, requirement) 槽（consumed_binding 位图），
      requirement 必须小于该 active 的实际需求数，provider 必须 < active_count 且名字一致；
    - 链接边：count 必须等于 plan.edge_count 且不超过证据容量；每条记录消费一条尚未被消费的
      真实边（consumed_edge 位图）。
  三类共 4 条新用例（重复 3 条 + 容量越界 1 条）都驱动真实类别，且合法对照侧用同一实现断言
  "重复/越界必须被判不一致"，避免反向用例退化成假通过。

[14] 确定性与固定图语义（src/assembly/FixtureDeterminism.cpp）
  - 打乱 catalog 顺序、选中集合顺序、组内候选顺序后，规范化 active 表、拓扑序、
    逐需求 provider 与指纹逐项相同（static_assert）。
  - 同一上游满足下游两个不同需求：两条 provider 记录都保留，拓扑边只计一次（edge_count == 1）。
  - 未选后端形成的潜在环不误判：A 依赖 [B,C]、B 依赖 A、C 无上游。
    选中 {A,C} → 合法且只有 C→A 一条边；选中 {A,B} → 必须报 Cycle。

3. 常量求值成本与最大合法规模（本机、默认限制）
--------------------------------------------------------------------------------
先说结论（**默认限制**与**有限目标参数**两套，必须分开读）：
  A. 默认 -fconstexpr-ops-limit=33554432（不加任何编译参数）：
     - 本轮优化后实测通过的最大组合是 **128 active / 256 catalog / 32 需求 / 每组 8 候选**
       （28,544 个候选叶子），目标 fixture_scale_max_legal_128x32x8（exit 0，强制重编 10.68 s）；
     - 优化前该档是失败的，当时的默认最大档是 32×4（14,272 叶子，3.6 s）。也就是说
       本轮把默认预算下的合法上界提高了一倍候选数。
     - 满组合 128/256/32/16（57,088 叶子）在默认限制下**仍然失败**
       （raw/scale-fixture_scale_limit_128x32x16-r2.log，exit 2，6.69 s，
       错误文本 "'constexpr' evaluation operation count exceeds limit of 33554432"）。
     - 因此**不能**宣称"推荐最大规模在默认限制通过"。
  B. 有限目标参数 -fconstexpr-ops-limit=134217728（只加在 fixture_scale_target_128x32x16）：
     - 满组合真实编译通过，exit 0，16.24 s
       （raw/scale-fixture_scale_target_128x32x16-r2.log）；
     - TU 内不是"只要编译过就算"，而是断言 error==None、active_count==128、
       去重边数==3568（= 逐需求绑定总数）、最后一个 active 的首个需求绑定到上一个插件、指纹非 0；
     - 参数的依据、生效核实、作用范围与未测编译器见第 1 节；这是"有证据的有限参数"，
       不是把默认限制的失败抹掉。
  C. P1 仍必须继续优化：默认预算下满组合未通过是明确的阻塞项（见 D2）。

成本分析（沿用上一轮的结论，本轮补充定位）：
  上一轮已做过的消融证明：收集/建索引/建 active 表在满规模下只要 1.5~1.6 s 就通过，
  超限全部发生在**逐候选的校验/绑定阶段**；成本 ~ 候选叶子数 × 每次候选的常量求值语句数。
  本轮在这个基础上处理四类可量化的浪费：
    (1) 每个候选要跑 4 趟名字循环（格式校验 / 复制 / 前缀字 / FNV-1a）→ 合并成 1 趟；
    (2) 声明期还有一次 O(k²) 的同组重复前缀扫描（k 最多 16，等于每候选最多 15 次 same_name）
        → 删除，改为绑定阶段用 catalog 下标位图 O(k) 判重（类别仍为 DuplicateCandidate）；
    (3) 每个候选是一个 144 字节的 PluginIdentity 对象（含 bool/count/padding），构造、写入、
        读取都要按对象整体计费 → 改成 SoA 紧凑键（5 个标量）+ 名字池；
    (4) 建图/指纹/证据比对按每 active 固定 32 个需求槽遍历，而实际需求数常常远小于 32
        → 记录 active_requirement，按实际需求数遍历，provider 也不再整体预填哨兵。

本轮实现优化（三个接口、拥有存储语义、完整 catalog 候选校验、唯一 provider 语义都没变）：
  a. detail::identity_from_chars 单趟完成"校验 + 复制 + 前缀字 + FNV-1a"；
  b. 候选改成紧凑拥有存储：candidate_length / candidate_offset / candidate_id /
     candidate_prefix0 / candidate_prefix1 + candidate_pool（名字字节按实际长度写入）；
     读候选只碰标量，名字比较走 name_equals（先比键、必要时逐字节），
     不允许"只比哈希"或返回 view；
  c. add_candidate 去掉 O(k²) 重复扫描（判重下移到 bind_entry 的位图）；
  d. AssemblyResult 增加 active_requirement；build_graph / fingerprint / compare_evidence
     都按实际需求数遍历，不再每 active 固定 32；
  e. bind_entry 的自依赖判等改为完整名字相等（见 [13]），并在绑定成功时写 active_requirement。

本轮实测（同一方法 = g++ -fsyntax-only -O3 -DNDEBUG -std=c++20 直接测 scale_probe.cpp，
完整命令/退出码/秒数在 raw/scale-opt-<label>.log）：
  label                        组合                 结果           秒数
  128x32x4-default            128/256/32/4         exit 0         4.89
  128x32x8-default            128/256/32/8         exit 0         10.22     ← 优化前该档失败
  128x32x16-default           128/256/32/16        exit 1         5.79
  128x32x16-67108864          128/256/32/16        exit 0         14.51     ← 优化前该档失败
  128x32x16-134217728         128/256/32/16        exit 0         14.80
  与上一轮记录对比（注意方法/负载不同，只有"通过与否"和"需要多少预算"可直接比）：
  - 上一轮：默认最大档 32×4；32×8 失败；32×16 需要 134,217,728（67,108,864 仍失败，17.3 s）。
  - 本轮：默认最大档 32×8；32×16 在 67,108,864 已能通过，134,217,728 仍有富余。
    结论：候选级操作数至少下降一半以上（同一预算能容纳 2 倍候选）。
  - 绝对秒数本轮普遍偏高（32×4：上一轮 3.0 s → 本轮 4.89 s；32×16@134M：7.9 s → 14.8 s），
    与机器当前负载/会话有关，**不能**当作"变慢"的性能结论，也不能反过来当作加速证明。

规模阶梯（cmake --build cmake-build-protoshared --target <target>，每个目标先 touch 源文件
强制重编；完整输出与秒数在 raw/scale-<target>-r2.log）：

  fixture_scale_active_128              128 / 128 / 0  / 1    通过     1.23 s

  失败信息：'constexpr' evaluation operation count exceeds limit of 33554432
  （这是 ops 上限，不是 loop iteration 上限；loop 上限 262144 在更早的探针里单独确认过）。

--------------------------------------------------------------------------------
4. 已发现的缺陷/风险（供 P1/P2，不在 P0 擅自修复）
--------------------------------------------------------------------------------
D1. 模块桩不会被自动抽取（已在本 fixture 内用"只对桩做 whole-archive"绕过）。
    生产 id_add_plugin 目前用 target_link_libraries(... PRIVATE IDPluginStub)，
    对从不分配的模块不会抽到桩对象 → 这些模块里的 new/delete 会落到 CRT。
    P2 应决定统一的保留机制（桩专用 whole-archive/WHOLEARCHIVE 或对象注入），并逐模块验证符号。

D2. 声明数据结构的编译期成本仍然过高（本轮从 32×4 优化到 32×8，32×16 仍未进默认预算）。
    已完成：候选改成 SoA 紧凑键 + 名字池（不再逐候选 144 字节结构）、声明单趟化、
    去掉 O(k²) 判重、按实际需求数建图/指纹。结果见第 3 节。
    仍未解决的部分（P1）：
    - 名字池按"候选上限 × 名字上限"预留，即使实际名字都很短也要占 96 字节/候选；
      这是"拥有存储 + 长度只在值里"这一约束下的最坏情况上界。真正的紧凑化需要让池容量
      与"实际名字总长"挂钩（例如生成器把总长作为模板参数带进来），否则 57k 叶子仍是 ~5.5 MB。
    - PlanState 仍是"按容量上限定长"的工作区（catalog 身份 256×144 字节 + 槽表 + 边表），
      每次 sort_and_validate 都要整体初始化；P1 应按实际 catalog/需求规模参数化。
    在完成这些之前，**不要**把"每组 16 候选"当成默认限制下的已达成契约；
    本轮满组合的通过依赖第 1 节那条有限的 -fconstexpr-ops-limit=134217728。

D3. 既有 benchmark 指标 plugin.service_lookup_and_call 在 MONOLITHIC=ON + LTO 下会被常量折叠
    （actual=n/a、ungraded、SUMMARY 记 1 failed），而同一份代码 MONOLITHIC=OFF 下是 0.25 ns。
    这是改造前就存在的问题，本次未改该指标实现。baseline 里的 0.23 ns 只能当"同一构建、
    相邻时段"的保存读数，不能用来证明"热路径没有额外间接层"（见基线文件 4/5 节与 7.2）。
    做 STATIC/SHARED 对比前必须先让该指标不可折叠，并由 benchmark-developer 另派测量。

D4. CMake 侧只做 schema/名字/唯一 provider 预检；能力、槽位、接口修订的唯一性仍是 P1/P2 范围
    （本原型不含 capability/slot 契约，fixture 只用"需求组候选集合"表达需求）。
    计划书 §16.1 里"槽 63/槽 64""同 capability/同 slot 两个提供者""接口修订不达标""宏冲突"
    等条目本 P0 未覆盖，属于 P1/P2。

D5. 运行期完全沿用旧路径：`ID::PluginManager::instance()` 单例 + fixture 自己的四阶段绑定表
    （FixtureProductEntry.cpp），没有 PluginRuntime、没有状态机、没有槽位所有权检查。
    P0 只证明"编译期计划 + 真实链接 + 回调被调用"，不证明运行期契约。

D6. 反向用例的错误优先级在合并校验/绑定后与旧实现略有差异（如实保留，不掩盖）：
    旧实现先校验完 catalog 全部条目再绑定；新实现按 catalog 顺序边校验边绑定
    （同一插件内仍然"先校验后写 provider 行"）。
    本轮又移动了一条：组内重复候选从"声明期"下移到"绑定阶段"（用 catalog 下标位图判重），
    因此它相对其它类别的先后可能与旧实现不同。
    对单错误输入（全部 28 条反向用例都是单错误）结果相同；**同时存在多个错误时报告的类别
    可能与旧实现不同**。计划书 §7 没有规定多错误优先级，这里作为已知行为记录；
    多错误的确定性优先级属于 P1 待定义项（需要先定义"哪个错误先报"的规则，再补用例），
    本轮不擅自发明规则。
    内部阶段顺序（当前实现，不是契约）：收集/容量复核 → catalog 同名/碰撞索引 → active 规范化
    （未知/重复/上限）→ 逐候选校验与绑定（候选格式、自依赖、未知候选、组内重复、
    缺失/歧义 provider）→ 建图与环 → 指纹。

D7. 本轮的测量方法边界（避免误读第 3 节）：
    - 跨轮次的绝对秒数不可比（不同会话、不同机器负载、cmake 构建含 make 开销）；
      可比的只有"同一预算下通过/失败"和"满组合需要多少预算"。
    - 32×16 通过依赖的是有限编译参数（第 1 节），默认限制下仍失败；
      因此本文件同时保留"默认限制失败目标"和"有限参数通过目标"两份证据，缺一不可。
    - 编译期成本不是运行时性能：本轮没有任何 Benchmark 指标改动，也没有新的性能评级。

8.4 核验结果（可逐条复核）
  - 两个目录各 36 个文件 = 28 条 case 日志 + legal-control + wrong_expectation +
    aux_assert_failure + summary + index + batch-owner + 批次 stdout + 批次命令记录。
  - 28×2 条 case 日志逐文件统计（python 读取日志文本，按 "static assertion failed" /
    "ID_ASSEMBLY_ERROR_EXPECTED:" / "ID_ASSEMBLY_ERROR_MISMATCH" 计数）：
    失败条数全部为 1、EXPECTED 全部为 1、MISMATCH 全部为 0；EXIT 全部为 2；
    每条都带本模式的 MODE 与 BUILD_DIR。
  - 自检一：EXIT=2、失败条数=1、HAS_MISMATCH=TRUE → 拒绝理由"错误类别不符（出现 MISMATCH 标记）"。
  - 自检二：EXIT=2、失败条数=2、HAS_EXPECTED=TRUE、HAS_MISMATCH=FALSE → 拒绝理由
    "失败断言数=2（判据要求恰好 1 条…）"，GCC 另提示 "the comparison reduces to '(0 == 2)'"。
  - 互不覆盖（最后一次运行）：28 条 case 日志时间窗 protoshared 18:23:59–18:24:14、
    protostatic 18:24:19–18:24:33，两窗不重叠；每条日志头部的 MODE / BUILD_DIR 与所在目录
    一致——一旦被另一模式覆盖，这两个字段立刻暴露。索引 STARTED/FINISHED 与批次 stdout

10.1 本轮范围

10.2 缺陷 1（MSVC 下 lambda 体内调用 consteval）复现 -> 修复
  复现（修复前真实构建，MSVC 19.52 + 生成器 Visual Studio 18 2026，Debug）：
    cmake --build cmake-build-msvc-protofix2 --config Debug --target FixturePrototype
      exit 1：FixtureDeterminism.cpp(175,16) error C7595「对即时函数的调用不是常量表达式」×1
              FixtureDeterminism.cpp(166/179/180/182) error C2131「表达式的计算结果不是常数」×4
              日志 raw/msvc-protofix2/msvc-build-repro-defect1.log
    根因：第 4 节把 consteval 的 sort_and_validate 调用写在就地 lambda 体内，GCC 接受、MSVC 不接受。
  修复（只换包装，不动断言）：提成命名 consteval 函数，与第 3 节 make_determinism_plan 同一写法
    consteval auto make_shared_upstream_plan() noexcept { ...原 lambda 函数体逐字保留... }
    constexpr auto kSharedUpstream = make_shared_upstream_plan();
  语义等价证据：
    - 函数体逐字保留：同名 register_plugin、同样两条需求、同样的 sort_and_validate 调用与实参顺序；
    - 没有增删或弱化任何断言：当前文件 static_assert 行数 22；第 4 节的 3 条断言
      （error == None、edge_count == 1、两个需求各自保留绑定）一字未动；
    - 全文件 lambda 计数 = 0；命名 consteval 函数 3 个
      （make_determinism_plan / make_shared_upstream_plan / make_potential_cycle_plan）；
    - GCC 侧同一份代码仍编译通过并运行通过（见 10.5），说明没有改成任一编译器专用写法。
10.3 缺陷 2（多配置生成器下 DLL 与 exe 不同目录）复现 -> 修复
  复现（修复前真实运行）：多配置生成器给 RUNTIME_OUTPUT_DIRECTORY 自动追加 /Debug，
    exe 落在 out/bin/Debug，而 idf_copy_kernel_runtime 仍把 ID.dll 复制到 out/bin：
      out/bin/ID.dll（错位副本）  vs  out/bin/Debug/FixtureZeroPrototype.exe
    运行 out\bin\Debug\FixtureZeroPrototype.exe -> exit -1073741515（0xC0000135，DLL 未找到），无任何输出
      日志 raw/msvc-protofix2/msvc-run-repro-defect2.log
  修复：复制目标由 ${IDF_OUT_BIN} 改为 $<TARGET_FILE_DIR:${TARGET}>，即复制到该可执行文件的真实运行目录，
    多配置下自动带 /Debug、/Release、/MinSizeRel、/RelWithDebInfo。
    vcxproj 实测四份逐配置命令（raw/msvc-protofix2/msvc-artifacts.log）：
      cmake -E copy_if_different .../out/shared/bin/Debug/ID.dll        .../prototype/out/bin/Debug
      cmake -E copy_if_different .../out/shared/bin/Release/ID.dll      .../prototype/out/bin/Release
      cmake -E copy_if_different .../out/shared/bin/MinSizeRel/ID.dll   .../prototype/out/bin/MinSizeRel
      cmake -E copy_if_different .../out/shared/bin/RelWithDebInfo/ID.dll .../prototype/out/bin/RelWithDebInfo
