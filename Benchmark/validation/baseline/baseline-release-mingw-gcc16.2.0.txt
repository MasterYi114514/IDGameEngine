4. 性能基线（Release，同一构建连续 5 次；raw/release-r1..5.log）
--------------------------------------------------------------------------------
指标口径（既有实现，本次未改动）：
  - 每条指标都在同一轮、同一进程内测对照实现，参考值 = 同轮对照实测 × 目标倍数。
  - 单轮目标 100 ms，5 轮取中位数；单次迭代数按标定放大（上限 1<<26）。
  - 极差 > 20% 时用例自己在 note 里追加 unstable。

指标 1：plugin.service_lookup_and_call（本次重点比对的基线指标）
  轮次      actual       reference(=control*1.2)   ratio   grade
  r1        0.23 ns      0.41 ns [os-baseline]     0.55    excellent
  r2        0.23 ns      0.40 ns [os-baseline]     0.57    excellent
  r3        0.23 ns      0.40 ns [os-baseline]     0.57    excellent
  r4        0.23 ns      0.39 ns [os-baseline]     0.60    excellent
  r5        0.23 ns      0.40 ns [os-baseline]     0.57    excellent
  5 次中位数 0.23 ns；极差 (0.23-0.23)/0.23 = 0%；等级 5/5 稳定 excellent。
  同轮对照（volatile 全局函数表指针 + 间接调用）= 0.39~0.41 ns。
  该读数只作为"同一构建、相邻时段"的保存基线使用：待测路径没有 volatile 防优化，
  对照实现用了 volatile 全局表指针，两侧防优化强度不对称；同一指标在
  MONOLITHIC=ON + LTO 下已被实测折叠成 n/a/ungraded（见本文件 7.2 与
  D3 记录）。因此**不能**用这条 ns 读数证明"热路径没有额外间接层"，
  也没有目标代码（反汇编）证据；需要下该结论时必须另做不可折叠的测量并附反汇编。
  此读数只对本机、本构建、本次运行成立。

5. 本基线的局限（必须随结论一起引用）
--------------------------------------------------------------------------------
1. 只有 MinGW/GCC 16.2.0 + Release + MONOLITHIC=OFF 一组实测数据；MSVC、clang、
   MONOLITHIC=ON、Debug 与其它机器均为未验证，不能把本机结论外推。
2. plugin.service_lookup_and_call 的绝对值在 0.2~0.4 ns 量级，接近"每次迭代一次 load +
   一次间接调用"的硬件下界；GCC 在 -O3 下可能把对照循环与待测循环各自强度削减，因此该
   指标适合做同机前后对比（ratio 与等级），不适合当绝对性能目标。
   （2026-10-20 补充：事后反汇编确认这两条 0.2~0.4 ns 读数的默认路径**没有**执行间接调用，
   属去虚拟化口径；修正与不可比说明见第 6 节末行与 validation/perf-getservice-evidence.txt 第 10 节。）
3. 既有实现自身在部分运行会标 unstable（如 Debug 下 512B 与槽位查房的 5 轮极差 23%~29%），
   说明本机存在调度/调频噪声；本次 Release 5 次运行未触发 unstable，但不代表噪声消失。
4. report.txt 是唯一报告文件，每次运行覆盖；上面的 raw/*.log 是 console 文本证据，不是
   第二份报告，任何历史读数都必须连同 raw 日志与本文件的构建参数一起引用。
5. bin/ 下 Debug 与 Release 共用目录，本次构建后 bin 中的产物是 Release；如果后续要跑
   Debug 版本，需要重新构建，不能依赖残留产物。

6. 后续（P1+）对比规则
--------------------------------------------------------------------------------
- 只与第 4 节的 Release 基线比较：同机、同编译器、同构建类型、同优化参数、同计时设置。
- 先确认 report.txt 的 build 行与本文件一致，再看 plugin.service_lookup_and_call 的
  actual / ratio / grade 与 note 是否带 unstable。
- 指标名 plugin.service_lookup_and_call 不无故改名（计划书 16.4 要求）。
- 若后续实现让该指标显著变化，必须同时给出 get_service 路径的目标代码证据（例如
  objdump 反汇编），不能只用 ns 数值推断是否存在额外间接层。
- 2026-10-20 口径变更：该指标的被测表达式与同轮对照都改为经空 asm 屏障后**真实执行一次间接
  调用**（证据：validation/perf-getservice-evidence.txt 第 10 节）。第 4 节与 7.1 节记录的
  0.23~0.25 ns 属去虚拟化口径，与修正后的 1.59 ns **不可直接比较**，不能再当回归基线；
  引用本文件时必须同时说明这一点。

7.2 MONOLITHIC=ON（STATIC 内核 + LTO）下的观察——测量健壮性问题，改造前即存在：
    同一份 kernel_performance.cpp 在该模式下得到
      plugin.service_lookup_and_call  actual = n/a（实际算成 <= 0）→ ungraded → SUMMARY 记 1 failed
    原因是 LTO 下 mix_round 与槽位数组都被内联/常量折叠，整段循环可被闭式求值。
    该次运行的 metric 观察记录：Benchmark/validation/baseline/raw/monolithic-metric-observation.log
    影响：P1 若要比较 STATIC 与 SHARED 两种产品，必须先让该指标不可折叠（例如让表指针来自
    跨 TU 的 volatile 或从真实插件读取），否则 STATIC 侧永远得到 ungraded + FAIL。
    本次未修改该指标实现（属于既有 Benchmark 资产），只记录事实。
